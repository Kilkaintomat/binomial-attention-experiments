# Две языковые задачи с биномиальным вниманием — протокол 5 ноября 2026

Это новая кампания, отдельная от HotpotQA/MuSiQue и архивных графов, Maze и Sudoku. Основных результатов этой кампании при подготовке протокола ещё нет. Существующие файлы и задания обучения сохраняются. Новые вычисления выполняются через Slurm; GPU-этап следует за завершением оставшейся MLP-серии.

## Математика и замена в архитектуре

```math
A=\mathrm{softmax}\!\left(QK^\top/\sqrt{d_k}+M_{\mathrm{causal,padding}}\right),\qquad O=P_r(A)V,\qquad P_r(A)=\frac{(I+A)^r-I}{2^r-1}=\sum_{s=1}^r\frac{\binom{r}{s}}{2^r-1}A^s.
```

Это нормированный positive-hop оператор статьи: нулевой член исключён, внешний residual сохраняется один раз. В старых Qwen-сериях использовалась также интерполяция `AV + g(P(A)V − AV)`; здесь чистый фильтр соответствует фиксированному `g=1`, обучаемого gate нет. Внутри степеней нет MLP, нормализации или пересчёта QK. Обычные output projection, внешние residual, normalization и FFN остаются.

`A` строится один раз в голове/слое при каждом полном forward и участвует в autograd при каждом использовании. Разрешены все текущие и предыдущие непустые позиции. Маршрут, правильный ответ и adjacency mask в модель не передаются. Вычисляются произведения `A @ Z`, а не плотные степени матриц.

Устойчивая рекурсия заимствована из существующего корректного фильтра:

```math
z_0=V,\quad u_0=0,\quad t_k=Az_k,\quad z_{k+1}=(z_k+t_k)/2,\quad u_{k+1}=(u_k+t_k)/2,\quad O=u_r/(1-2^{-r}).
```

Она избегает экспоненциального усиления и вычитания близких чисел. `P1(A)V=AV`. BF16 остаётся конечной точностью: oracle и математические сравнения отдельно проверяются в FP64/FP32, BF16 проверяется на конечность и реальных обновлениях.

Геометрический контроль имеет положительные веса, пропорциональные `rho^(s−1)`, для `s=1..r`. Параметр rho определяется численно так, чтобы средняя степень совпадала с биномиальной:

```math
\mathbb E S=\frac{r}{2(1-2^{-r})}.
```

В основном обучении `r=8`, средняя степень приблизительно 4,016. Это не восемь гарантированных семантических шагов. `r=8` фиксируется заранее; pilot не выбирает r по глубокому тесту.

Для всех моделей используется **полный префикс без KV-cache**, при обучении и каждом шаге greedy generation. Существующий transport-cache не переиспользуется с новой рекурсией без отдельной проверки. Измерения времени у всех вариантов учитывают одинаковый cache-free режим.

## Variable tracking: явная адаптация RULER

В стандартном генераторе [NVIDIA/RULER](https://github.com/NVIDIA/RULER/blob/main/scripts/data/synthetic/variable_tracking.py) запрос перечисляет переменные с указанным значением. Здесь вопрос другой: вернуть **значение одной конечной переменной**. Это адаптация, а не воспроизведение стандартного RULER VT или его benchmark-score.

В каждом примере несколько независимых цепочек. Начальные значения различны и равномерно выбираются из 16 названий цветов. Имена переменных случайно выбираются без повторений из 256 имён; числовая часть имени не кодирует глубину или цепочку. Используются шаблоны `v013 = red ;` и `v094 copies v013 ;`/`v094 = v013 ;`. Переопределений нет. Внутри каждой цепочки порядок причинный, между цепочками — случайное перемешивание. Между записями случайно размещён filler из слов quiet/cloud/stone/river.

Train: целевая глубина 1–4, четыре цепочки, длина 256 или 512 слов. Глубины трёх посторонних цепочек независимо выбираются из 1–4. Test: целевая глубина 1,2,3,4,8,16,32 при длинах **512 и 1024 слова для каждой глубины**, четыре цепочки, 64 примера на ячейку. Дополнительный срез помех: глубины 4/16, длина 1024, две/восемь цепочек, 32 примера на ячейку. Всего test 1024 примера.

Scratch получает один токен на слово плюс BOS. Входной словарь заранее конечен; проверяется, что каждый тестовый входной символ встречался в train. Это новые комбинации известных имён, а не испытание необученных embeddings. Для Qwen длина выравнивается **после его токенизации**: 512/768/1536/3072 токена для исходных длин 128/256/512/1024 слова. Префиксный filler не содержит присваиваний. Таким образом, основной тест глубины имеет одинаковую действительную длину входа внутри каждого tokenizer; длина и глубина не смешиваются.

Основной loss использует только конечное значение и EOS. Отдельная диагностическая разметка содержит позиции источника и цепочки, но её не получает forward или loss. Якорь записи — её завершающая точка с запятой, уже видящая всю запись причинно.

## p-hop induction: точное правило и два режима

Используется [Saunshi et al., Definition A.1](https://arxiv.org/html/2502.17416v1#A1.Thmdefinition1), а не обычный поиск повторяющейся буквы. Для индексов от 1:

```math
f(v,i)=\max\bigl(\{0\}\cup\{j:2\le j\le i,\ v_{j-1}=v_i\}\bigr),\quad f(v,0)=0,\quad i_0=n,\quad i_{t+1}=f(v,i_t).
```

Ответ — `v[i_p]`, либо BOTTOM при `i_p=0`. В частности, прежнее совпадение непосредственно перед текущей позицией даёт **самопетлю**, поскольку возвращается следующая за совпадением позиция. Примеры: `ABAB`, p=1 → A, p=2 → B, p=3 → BOTTOM; `ABB`, любое положительное p → B. Реализованы два независимых solver: буквальный поиск максимума и заранее вычисленный массив последних вхождений.

Авторский исполняемый код для этой статьи в просмотренных ссылках не найден; определение сверено с первоисточником, самостоятельная реализация не названа авторским кодом. [Sanford et al.](https://proceedings.mlr.press/v235/sanford24a.html) — теоретический источник постановки.

1. **Канонический контроль**: отдельные обучения при фиксированном p=16 и p=32, независимые iid-последовательности длины 256 из алфавита A/B/C/D. p фиксировано самим условием обучения. Размер модели, optimizer и объём обучения отличаются от исходной статьи; это не численная реплика её результатов.
2. **Условная адаптация**: train p=1–4, test p=1,2,3,4,8,16,32. Во входе всех моделей явно присутствует `Steps : | | ...`, ровно p одинаковых черт. На test нет новых токенов для чисел 8/16/32. Метка вычисляется после ровно p переходов.

В условной адаптации половина train — iid, половина — дополнительное распределение без соседних одинаковых символов. Эта доля независима от p. Test публикуется **раздельно** для iid и `no_adjacent`; результаты не выдаются за канонический iid. На каждом p/распределении 64 примера длины последовательности 256. Дополнительный контекстный срез — p=4/16, длина 512, по 32 примера. Всего 1024 test-примера. Для каждого фиксированного канонического p — 512 test-примеров.

Сохраняются весь путь указателя, самопетля, BOTTOM и число переходов, реально изменивших состояние. Отдельный срез `nontrivial` требует p действительных изменений без BOTTOM. Нулевое число примеров в подгруппе обозначается `n=0`, accuracy не выдумывается. После генерации в выбранных больших контекстах BOTTOM не встретился; это зафиксированная особенность выборки, а не результат обучения.

На binomial-checkpoint p-hop дополнительно оценивается замена фильтра на `A^p V` при том же доступном p, без дообучения. Это диагностическая смена оператора, а не отдельная основная обученная модель. Два подготовительных scratch-слоя остаются у всех архитектур. Применение фильтра в нескольких слоях не приравнивается автоматически к p семантическим шагам. Controller завершения и поглощающая маска в обучаемую модель не добавляются.

Всего **66 основных обучений**, две оценки исходной LM, шесть pilot-обучений и технические проверки. Это не декартово произведение всех r, слоёв, длины, режимов данных и seed: большие r/loops — оценки фиксированных checkpoints.

Scratch: Qwen3 decoder с нуля, четыре блока, ширина 256, FFN 1024, восемь голов Q и четыре KV, head_dim=32, RoPE. Первые два слоя обычные, последние два используют выбранный фильтр. Baseline имеет те же параметры; looped выполняет весь тот же backbone дважды с общими весами, включая оба подготовительных слоя. Все параметры scratch обучаются.

Pretrained: Qwen3-1.7B, revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`. Основные изменяемые слои — 26/27 (нумерация от нуля), абляция — 24/25/26/27. Все головы этих слоёв изменяются. Выбор сделан до просмотра глубоких модельных результатов. LoRA r=16, alpha=32, dropout=0 на Q/K/V/O во всех 28 блоках; base weights заморожены. Поэтому Q/K выбранных слоёв могут адаптироваться. У ordinary fine-tuning тот же режим обучаемых параметров и те же примеры.

Train по каждой из четырёх постановок: 16384 фиксированных примера; validation 256; pilot-only 128; tiny 8. Seeds генераторов train/validation/test/pilot/tiny: 710001/720001/730001/740001/750001 с фиксированными task/index offsets. Проверяется отсутствие точных дубликатов prompt внутри/между splits одной постановки. Данные разных постановок не смешиваются в одном основном обучении; исключение — явно определённая смесь iid/no_adjacent внутри условной p-hop адаптации.

Основной LR scratch выбирается **только по финальной короткой validation обычного VT baseline** из двух pilot LR; при равенстве берётся меньший. Эта же ставка применяется ко всем четырём scratch-архитектурам. Updates: 8000 при pilot accuracy ≥0,5, иначе 16000; это правило задано до pilot. Используются финальные веса, checkpoint не выбирается по test. Отдельные validation curves сохраняются на 500/1000/2000/4000/8000/16000 доступных updates. После каждого ordinary VT pilot оцениваются 128 отдельных pilot-only примеров; записываются ячейки глубина/контекст и ближайшая к 50% accuracy. Эта область не меняет основной test.

AdamW: weight decay 0,01; warmup 5% updates; cosine до 0,1 начального LR; clip grad norm 1. Scratch batch=32, microbatch=8. Qwen LR=0,0001, batch=8, microbatch=1. Сначала выбирается глубина, затем общий batch этой глубины; последовательность batch совпадает между архитектурами при одинаковом seed. Для каждого примера усредняется cross-entropy только по answer+EOS, затем усредняется по примерам. Prompt и padding исключены из loss. BF16 autocast на GPU, scratch weights FP32; Qwen base BF16, LoRA — штатная PEFT. TF32 и reduced-precision BF16 reduction отключены. Attention dropout отсутствует.

Tiny overfit должен дать минимум 7/8 exact match у baseline и binomial на обеих задачах за максимум 2000 updates. Его отказ останавливает продвижение новой кампании и сохраняет ошибку. Qwen fine-tuning разрешается лишь после завершения scratch и проверки ordinary baseline на короткой validation: на всех трёх seed каждой основной задачи accuracy не ниже `max(25%, majority+10 п.п.)`. При отказе дорогой этап не выдаётся за запущенный; остаются логи для диагностики. Старые задания не останавливаются ни при одном из этих отказов.

## Оценки, причинная диагностика и графики

Ответ без CoT, Qwen thinking disabled; unconstrained greedy, максимум восемь выходных токенов, остановка на EOS. Основная accuracy — строгое совпадение строки после удаления пробелов по краям. Вероятность ответа — произведение условных вероятностей **всех токенов эталонной строки без EOS**; отдельно сохраняется log probability. Она не подменяет фактический greedy exact match.

На binomial-checkpoint: r=1,2,4,8,16,32,64,80,96. На looped-checkpoint: loops=1,2,4,8,16. Сетка фиксирована, веса не меняются. Для этих затратных срезов заранее берутся первые восемь примеров каждой глубины/распределения из фиксированного test. Основная оценка использует весь заявленный test, а не только этот срез.

Масса оператора, вероятность строки и exact match сохраняются отдельно. Для VT query — последний токен входного префикса; targets — все токены исходного значения выбранной цепочки. Диагностика пути использует окончания записей. Номинальная аннотированная длина с query→конечная запись и root-record→value равна depth+2; она явно **не объявляется фактической длиной выученного маршрута**. Прямые массы правильных аннотированных рёбер также сохраняются.

Агрегация заранее фиксирована: среднее по всем головам каждого выбранного слоя, затем среднее по выбранным слоям; дополнительно сохраняются значения каждой головы. Лучшая голова задним числом не выбирается. Диагностический forward и teacher forcing выполняются вне интервала измерения свободной генерации. Сохраняются prefill, полное время ответа и peak GPU memory.

```math
m_\ell(r)=\Pr(S\ge\ell)=\frac{\sum_{s=\ell}^r\binom{r}{s}}{2^r-1},\qquad S\sim\mathrm{Bin}(r,1/2)\mid S>0.
```

Равенство с массой источника проверяется отдельно на известной цепочке с поглощающим состоянием. Это oracle-тест реализации, не доказательство accuracy LM. График oracle имеет log-log оси и y=x; нулевые пары исключаются с указанием количества. Для выученных маршрутов показывается отдельный график с теоретическим ориентиром при аннотированной длине, без предположения равенства; нули отмечаются порогом 1e-12 и сохраняются точно в CSV.

`report.py` строит CSV по каждому seed, среднее и выборочный SD, accuracy–hops, accuracy–r, accuracy–context, accuracy–distractors, validation-quality–training-time, измеренную массу–хвост. Canonical и адаптации различаются в таблицах. Кривые качества–времени служат сравнением вычислительной цены recurrent и остальных моделей; одинаковое число параметров не считается одинаковым FLOP-бюджетом. Все negative results сохраняются.

## Очередь, budget и воспроизводимость

До завершения 36 MLP-прогонов новый контроллер ставит только CPU-проверки/ожидание. Затем выполняется один GPU preflight и до двух независимых workers, по одной A100 на worker. Основные задания двухчасовые; промежуточные checkpoints сохраняются каждые 100 updates и перед штатным выходом. Сигнал/дедлайн завершает только новую worker-сессию с сохранением состояния. Общие исходники и модельный cache монтируются read-only; writable только новый каталог кампании.

Начальное отдельное разрешение новой кампании — **240 GPU-часов**, общий ориентир учёта — **500 GPU-часов**, с сохранением старых лимитов/ledger без редактирования. Это верхняя граница расходов, а не списанные часы и не обещание длительности. После фактического benchmark контроллер записывает оценку; если необходимый резерв выше, повышает новый лимит на основании явного текущего разрешения пользователя. По учёту оплачивается вся GPU allocation, включая preflight, ошибки, evaluation и сохранение. Pending jobs учитываются как резерв, после окончания заменяются фактическим Slurm ElapsedRaw. Неограниченного повторения ошибок нет.

Данные, manifest, source hashes, environment, model revision, trainable parameters, logs, checkpoints и failures сохраняются отдельно. Результат помечается completed только после всех запланированных предсказаний. Для продолжения используется тот же manifest и checkpoint; duplicate claims защищены, terminal stale claims восстанавливаются с журналом. Публикуются код, агрегированные метрики и hashes, а не частные документы, абсолютные пути, scheduler account или исходные пользовательские файлы.

Первый CPU-запуск уже проверил ядро и генераторы. Окончательная проверка включает также scheduler safety и заверяется хешем полной замороженной версии кода. GPU-профиль, pilot-оценка времени и основные accuracy до выполнения соответствующих Slurm-этапов считаются **неизмеренными**.
